# CogVideoX full-sequence and sparse RGB decode audit

**Reviewed:** 2026-10-17 (Asia/Shanghai)  
**Experiment:** `EXP-M1-COGVIDEOX5B-I2V-SMOKE-001`  
**Scope:** Static trace of the pinned Diffusers 0.40.0 CogVideoX image-to-video pipeline and `AutoencoderKLCogVideoX`. No model weights, inference, tests, GPU/runtime, notebook cells, or external state changes were used.

## Decision

The registered 49-frame generation maps to 13 temporal latent positions, then the decoder returns all 49 RGB frames. The pinned pipeline accepts a generation length (`num_frames`) and an output type; it has no frame-index selector. With the same call settings and latent seed, choosing frames from the returned RGB sequence after the pipeline finishes does not change denoising, because the pipeline performs the output-type branch only after its scheduler loop. It also does not skip VAE decoding or reduce the decoder's peak working set.

For an anchor-only diagnostic, the source-supported path is therefore: run the same full-sequence call, decode all 49 frames, then select anchor indices from the returned frames. This can reduce later review, export, or storage work if non-anchor frames are discarded, but it cannot replace M1's all-49-frame score contract. `output_type="latent"` bypasses RGB decoding and returns the full final latent sequence; it does not request sparse RGB frames.

## Source trace

- The local [configuration](run_config.yaml#L38) requests 49 frames. The local [runner](run_m1.py#L488) calls the pipeline once per pass with that `num_frames`, the configured callback, and `output_type="pil"`; it then converts the complete returned sequence ([frame conversion](run_m1.py#L438)) and saves each frame ([frame save loop](run_m1.py#L477)). The same runner's baseline/replay path makes the two registered full-sequence calls ([execution path](run_m1.py#L965)).
- In pinned Diffusers, `CogVideoXImageToVideoPipeline.__call__` exposes `num_frames` and `output_type` but no frame-index or sparse-output argument ([signature](https://github.com/huggingface/diffusers/blob/v0.40.0/src/diffusers/pipelines/cogvideo/pipeline_cogvideox_image2video.py#L543-L567)). Its latent-length formula is `(num_frames - 1) // temporal_scale + 1`, giving 13 positions for 49 frames ([latent preparation](https://github.com/huggingface/diffusers/blob/v0.40.0/src/diffusers/pipelines/cogvideo/pipeline_cogvideox_image2video.py#L331-L379), [pipeline setup](https://github.com/huggingface/diffusers/blob/v0.40.0/src/diffusers/pipelines/cogvideo/pipeline_cogvideox_image2video.py#L712-L735)).
- The scheduler updates the latent sequence inside the denoising loop ([scheduler and callback](https://github.com/huggingface/diffusers/blob/v0.40.0/src/diffusers/pipelines/cogvideo/pipeline_cogvideox_image2video.py#L748-L814)). After that loop, `output_type != "latent"` calls `decode_latents` and postprocessing; `"latent"` returns `latents` directly ([output branch](https://github.com/huggingface/diffusers/blob/v0.40.0/src/diffusers/pipelines/cogvideo/pipeline_cogvideox_image2video.py#L816-L829)). The decode helper permutes the complete sequence and calls `vae.decode(...)` ([decode helper](https://github.com/huggingface/diffusers/blob/v0.40.0/src/diffusers/pipelines/cogvideo/pipeline_cogvideox_image2video.py#L380-L386)).
- `AutoencoderKLCogVideoX` internally decodes time in batches of two latent frames by default. Its source documents the 13-latent case as a first three-latent chunk `(0,1,2)`, followed by five two-latent chunks through `(11,12)`, yielding 49 RGB frames ([VAE defaults and derivation](https://github.com/huggingface/diffusers/blob/v0.40.0/src/diffusers/models/autoencoders/autoencoder_kl_cogvideox.py#L970-L1001)). `_decode` carries `conv_cache` between chunks, accumulates each decoded chunk, and concatenates them across time before returning ([decode loop](https://github.com/huggingface/diffusers/blob/v0.40.0/src/diffusers/models/autoencoders/autoencoder_kl_cogvideox.py#L1084-L1107)). This is memory-oriented internal temporal batching, not sparse RGB selection.

## Memory and latency implications

- VAE slicing only splits the batch dimension when the batch contains more than one sample ([decode slicing](https://github.com/huggingface/diffusers/blob/v0.40.0/src/diffusers/models/autoencoders/autoencoder_kl_cogvideox.py#L1110-L1129)). The M1 call uses one prompt and one video, so enabling slicing does not reduce its decode batch.
- VAE tiling splits overlapping spatial height/width regions. For the pinned 720×480 output, the source defaults imply half-size 360×240 sample tiles and 45×30 latent tiles; the 90×60 latent map exceeds both thresholds, so the runner's enabled tiling path is selected. The tiled decoder still loops over temporal chunks and concatenates each tile's full time axis before spatial blending ([tile defaults](https://github.com/huggingface/diffusers/blob/v0.40.0/src/diffusers/models/autoencoders/autoencoder_kl_cogvideox.py#L990-L1001), [tile routing](https://github.com/huggingface/diffusers/blob/v0.40.0/src/diffusers/models/autoencoders/autoencoder_kl_cogvideox.py#L1084-L1089), [spatial tile decode](https://github.com/huggingface/diffusers/blob/v0.40.0/src/diffusers/models/autoencoders/autoencoder_kl_cogvideox.py#L1212-L1285)).
- Spatial tiling should reduce per-tile VAE activation size and may increase latency because overlapping spatial regions are decoded and blended. Those are code-based expectations, not M1 measurements. No exact M1 VRAM or decode-latency result exists; the 2B example in the source is not transferred to the 5B run.
- Selecting a few PIL frames after the pipeline returns can reduce downstream files or review load, but it comes after full VAE decode. A custom cache-preserving decoder could potentially discard non-anchor RGB chunks before final concatenation while still traversing the full latent sequence; that would be an unvalidated implementation and would not remove the VAE convolution work. It is unnecessary for the registered M1 score table, which requires every decoded frame.
